# Safety Guard：赞助商奖项分析与开发建议

整理日期：2026-09-19  
比赛：[Hack the North 2026](https://hackthenorth2026.devpost.com/)  
状态：概念与开发规划，尚未实现或验证产品功能。

本文整理自本次对话中对官方比赛页面的核对。奖项与规则是当时的页面信息；匹配度、架构和开发顺序是设计建议。提交前应再次查看官方页面，实际参评需要满足相应实现条件。

## 1. 项目概念与定位

用户分享一笔 Uber 行程，创建守护任务，由另一位社区成员接受并在线关注行程。守护者完成约定的响应与确认后，获得社区声望和点数。真人暂时无法响应时，AI Agent 接力，继续确认乘客状态、理解求助，并按预先设置的权限执行基础通知和升级处理。

建议定位：

> 一个由真人与 AI 接力的行程守护网络，用链上记录支持守护承诺、贡献验证和社区激励。

产品需要体现的新增价值是：有人明确接受守护责任、失联时可以交接、响应过程可以追溯、实际贡献得到认可。

Uber 已提供实时行程分享，因此仅仅展示地图与分享链接的差异化有限。[Uber 行程分享说明](https://www.uber.com/us/en/ride/how-it-works/share-status/)

## 3. 建议的技术职责划分

以下为开发判断，尚未经实现验证。

| 层次 | 建议职责 | 首版要证明的事情 |
| --- | --- | --- |
| 乘客与守护者界面 | 创建任务、接单、确认状态、发送求助、查看接管状态 | 参与者能理解当前由谁守护、通知是否成功 |
| 链上合约 | 记录任务承诺、参与者、完成确认、贡献凭证和声望更新 | 一笔任务从创建到结算可追溯，重复结算会被拒绝 |
| 链下后端 | 保存行程状态、管理访问权限、检查超时、处理通知与重试 | 真人无响应后仍能持续推进守护流程 |
| AI Agent | 理解含糊消息、结合已有信息追问、选择受限工具、生成交接摘要 | 面对缺失或冲突的信息，可以说明不确定性并完成适当动作 |
| 外部服务 | 消息、语音、地图及经授权取得的行程数据 | 外部调用结果可以确认，失败能够被展示和处理 |

建议由 Solana 承担首版链上功能、Cloudflare Workers 承担守护后端。模型与消息供应商根据实际可用权限选择。以上是推荐组合，不代表已验证所有 SDK、额度或部署方式均可用。

### 区块链的用途

- 记录谁在何时接受了守护任务，以及约定的响应与完成规则。
- 根据经过确认的贡献更新社区声望和点数。
- 保留关键状态变化的凭证，便于事后核对。
- 首版可采用不可转让声望，减少直接购买声望带来的干扰。

AI 推理、位置接入、计时和通知应在链下运行。合约无法自行获知车辆位置、真人是否清醒或乘客是否安全，需要明确的外部事件提交机制。

链上记录能说明提交了什么、由谁提交、何时提交，不能单凭一条记录证明现实世界中的安全状态。首版必须明确谁有权确认完成、谁可写入任务事件。

## 4. 真人与 AI 的接力机制

不必先解决“识别守护者是否睡着”。首版可以使用可观察的触发条件：守护者没有在约定时间内确认响应。

建议把行程状态与守护模式分开管理：

- 行程状态：待接单、进行中、已完成、已取消。
- 守护模式：真人、AI 接力、等待备用真人接手。
- 异常事件单独记录，避免把“抵达”和“风险已解除”混为一个状态。

推荐流程：

1. 乘客创建任务，设置联系人与允许的通知动作。
2. 真人接受任务，明确确认节奏。
3. 真人确认超时，后端将守护模式切换为 AI 接力，并向乘客展示变化。
4. AI 根据可用信息确认乘客状态，必要时通知备用守护者。
5. 备用守护者确认接手后，获得当前状态和关键事件摘要。
6. 乘客确认抵达，任务按约定规则完成，贡献记录进入结算。

响应间隔、接管阈值和重试次数应可配置；目前没有经过验证的推荐数值。

AI 的首版动作范围建议限定为状态确认、信息整理、预先授权的联系人通知和人工接力。演示应区分“已尝试通知”“发送成功”和“对方已确认”。

## 5. 声望、点数与隐私

### 贡献如何计算

声望应对应实际服务，而不是仅凭接单或行程结束发放。可考虑响应记录、交接记录和乘客确认。真人失联期间由 AI 完成的工作，应分别记录。

首版至少需要防止同一任务重复结算。对刷单、多人串通和争议处理，应在演示中如实说明尚未解决的范围。

### 数据如何保存

- 精确位置、住址、联系方式、原始语音与聊天内容保留在受控的链下系统。
- 链上优先保存任务标识、参与关系、必要状态和凭证摘要。
- 行程共享仅对获授权的守护者可见，并考虑任务结束后的访问撤销。
- 不要公开能直接打开行程详情的分享链接。

## 6. Uber 接入是优先验证项

Uber 分享链接可以提供行程查看入口，但不自动赋予第三方应用读取实时数据的 API 权限。官方文档把包含实时位置的 `all_trips` 列为特权权限。[Uber Scopes 文档](https://developer.uber.com/docs/riders/guides/scopes)

开发前应确认：

1. 团队实际能获得哪些接口与授权。
2. 能否稳定取得行程状态、位置与时间戳。
3. 分享失效、网络断开或位置停止更新时，产品如何展示数据新鲜度。

如果比赛期间无法完成真实接入，可以用明确标注的模拟轨迹驱动演示，或使用乘客主动授权的位置分享。不能把模拟轨迹介绍成已经接通 Uber 实时 API。

## 7. 首版开发顺序

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 确认数据来源与基础界面 | 乘客可创建任务，另一账号可接单，双方看到一致状态 |
| 2 | 实现状态与超时处理 | 停止真人确认后，系统可见地进入 AI 接力 |
| 3 | 接入模型与一个真实通知渠道 | 含糊求助触发追问或通知；能够显示工具调用结果 |
| 4 | 实现链上任务与贡献记录 | 可查看创建、接单和完成交易，拒绝重复结算 |
| 5 | 加入噪声与失败场景 | 位置过期、消息延迟、通知失败时不会静默显示一切正常 |
| 6 | 按余力增加语音或多 Agent | 新功能对守护流程有明确作用，并可现场演示 |

不建议首版同时开发自建公链、多链桥、复杂代币经济或全面的自动紧急处置。先证明一笔行程可以完成可靠交接。

## 8. 推荐的现场演示

**分享行程 → 真人接单 → 真人响应超时 → AI 接管 → 乘客发出含糊求助 → AI 核验并通知备用守护者 → 乘客确认抵达 → 链上更新贡献。**

针对不同评委突出不同证据：

- **Solana**：展示真实交易与合约状态，以及链上记录在贡献核对中的作用。
- **Rox**：展示含糊消息、过期位置或信息冲突，以及 Agent 如何处理不确定性。
- **Cloudflare**：展示后端保存状态、触发超时、执行工具和处理失败的过程。
- **Linq／ElevenLabs**：展示真实消息或语音交互，以及它如何降低乘客操作负担。
- **OpenAI**：说明 API 的产品作用，并准备一个 Codex 改进开发结果的具体案例。

需要能回答：谁有权限查看行程、为何触发接管、消息是否送达、何时确认完成、如何避免重复奖励、数据或工具不可用时如何处理。

- 评审以现场运行演示为重点，提交需包含源代码及比赛期间创建的设计资产。

当前建议的申报组合是 **Solana＋Rox＋Cloudflare**。只有在相应集成真实完成且符合条件时，再增加消息、语音、模型或多 Agent 相关奖项。
